# [Ola 3 · 02] Reindexar memoria al cambiar de modelo de embedding

> Parte de la iniciativa **Xavier 100% Local (LLM + embeddings vía Ollama) — Ola 3**.
> Asegura la consistencia semántica cuando el usuario cambia de modelo de embedding.

## 🎯 Contexto

Los embeddings viven en la tabla `memory_embeddings` (`src/storage/migrations.rs:135-140`):

```sql
CREATE TABLE IF NOT EXISTS memory_embeddings (
    id TEXT PRIMARY KEY,
    workspace_id TEXT NOT NULL,
    embedding BLOB NOT NULL
);
```

**No existe columna `embedding_model` ni `dimension`**: los vectores se guardan como BLOB opaco.
El modelo activo viene de `XAVIER_EMBEDDING_MODEL` (o `settings.models.embedding_model`) y la
dimensión esperada de `XAVIER_EMBEDDING_DIMENSIONS` / `VecSqliteStoreConfig::embedding_dimensions`
(`src/memory/sqlite_vec_store/config.rs:23`).

La Ola 1 ya añadió la cache de embeddings **keyada por modelo** (`src/embedding/cache.rs:46`,
`EmbeddingCacheConfig::model_name`), de modo que la cache in-memory es consistente con el modelo.
Pero el **vector store persistente** (`memory_embeddings.embedding`) NO sabe con qué modelo se
generó cada vector. Si el usuario pasa de `embeddinggemma` (dim ~768) a `nomic-embed-text` (dim
768 igual pero espacio semántico distinto) o a cualquier modelo de otra dimensión, la
`hybrid_search_with_embedding` (`src/memory/sqlite_vec_store/mod.rs:238`) compara vectores
mezclados → resultados basura o crash por dimensión inconsistente en `sqlite-vec`.

El hook natural para detectar el cambio es `VecSqliteMemoryStore::init_schema_async`
(`src/memory/sqlite_vec_store/schema_impl.rs:31`), que ya corre al arranque y ya implementa
`migrate_embeddings_on_startup` (líneas 54–100). Allí se puede:

1. Leer el modelo activo de `EmbedderConfig::from_env()` (`src/embedding/mod.rs:103`).
2. Comparar con un "modelo activo guardado" persistido en una tabla metadata nueva.
3. Si difieren, marcar todos los `memory_embeddings` como pendientes de reindexado (p.ej.
   borrándolos o marcándolos con un flag) y loguear `warn!`.

El reindexado real ya existe: `POST /memory/reindex` → `reindex_handler`
(`src/cli/handlers/memory.rs:567`) recorre los `MemoryRecord` sin `embedding` y los reembebe.
**Bastaría con que la detección de cambio invalidara los embeddings antiguos** (seteando
`embedding = NULL` en `memory_records.embedding`, ya que `reindex_handler` los salta cuando
tienen embedding no vacío).

> Nota: el crate `xavier-core` está EXCLUIDO del workspace. Toda la lógica vive en el crate
> principal `xavier` (carpeta `src/`). **No tocar `xavier-core/`**.

## 📋 Problema

1. Cambiar `XAVIER_EMBEDDING_MODEL` deja silenciosamente la búsqueda semántica rota hasta que el
   usuario reinicia Xavier o se da cuenta de que los resultados no tienen sentido.
2. No hay huella persistente del modelo con el que se generaron los vectores.

## ✅ Criterio de aceptación

- [ ] Añadir una tabla metadata mínima vía una nueva migración V7 en
  `src/storage/migrations.rs` (siguiendo el patrón de `V6_UP` / `MigrationV6RecoverySystem`).
  Llámala `embedding_model_meta` con columnas `(key TEXT PRIMARY KEY, value TEXT)` o reutiliza
  una tabla `app_meta` existente si ya la hay (verificar antes).
- [ ] En `VecSqliteMemoryStore::init_schema_async` (`schema_impl.rs:31`) **después** de
  `migrate_embeddings_on_startup`, añadir una función
  `check_and_handle_embedding_model_change(conn, &active_model) -> Result<ReindexAction>` que:
  - Lea `active_model` desde `EmbedderConfig::from_env()` (el nombre del primer backend) o, si es
    `EmbedderConfig::Auto`, desde el sondeo de Ollama que ya hace `EmbedderConfig::from_env`.
  - Compare con el valor persistido en `embedding_model_meta.active`.
  - Si difieren (o no existe valor previo): setear `embedding = NULL` en todos los
    `memory_records` que tengan embedding, actualizar `embedding_model_meta.active = active_model`,
    y devolver `ReindexAction::Invalidated(n)`.
  - Si coinciden: devolver `ReindexAction::None`.
- [ ] Loguear con `tracing::warn!` cuando se invaliden vectores:
  `Embedding model changed from {} to {}: invalidated {} vectors. Run 'curl -X POST .../memory/reindex' or restart to rebuild.`
- [ ] **No** disparar el reindexado en el arranque (puede ser caro con miles de vectores y
  requerir Ollama disponible). Solo invalidar y dejarlo para el endpoint `/memory/reindex` o
  para que el `xavier doctor` (issue 04) lo reporte como acción pendiente.
- [ ] Test unitario en `#[cfg(test)] mod tests` de `schema_impl.rs` (o de `mod.rs`):
  - Caso A: primera vez → escribe el modelo y no invalida.
  - Caso B: mismo modelo → no invalida.
  - Caso B': modelo distinto → invalida todos los `memory_records.embedding` y actualiza meta.
- [ ] `cargo check --workspace` y `cargo test -p xavier --lib sqlite_vec_store` pasan.

## 🧪 Cómo verificar

```bash
cargo check --workspace
cargo test -p xavier --lib sqlite_vec_store
cargo test -p xavier --lib storage::migrations   # si hay tests de migraciones
```

En vivo:
```bash
# 1. Con un modelo instalado (p.ej. embeddinggemma), indexa algo:
XAVIER_EMBEDDING_MODEL=embeddinggemma xavier http 8006
curl -X POST localhost:8006/memory/add -H "X-Xavier-Token: ..." \
  -d '{"content":"test de embedding"}'

# 2. Para el server. Cambia el modelo:
XAVIER_EMBEDDING_MODEL=nomic-embed-text xavier http 8006
# 3. En el log de arranque debe aparecer:
#    "Embedding model changed from embeddinggemma to nomic-embed-text: invalidated N vectors."

# 4. Reindexa:
curl -X POST localhost:8006/memory/reindex -H "X-Xavier-Token: ..."
# 5. La búsqueda vuelve a devolver resultados coherentes.
```
