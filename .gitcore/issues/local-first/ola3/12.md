# [Ola 3 · 12] Validación de config al arranque (fail-fast claro)

> Parte de la iniciativa **Xavier 100% Local (LLM + embeddings vía Ollama) — Ola 3**.

## 🎯 Contexto

La config se carga en `src/main.rs:42`:

```rust
if let Some(settings) = XavierSettings::load()? {
    settings.apply_to_env();
}
```

`XavierSettings::load()` (`src/settings/mod.rs:26`) delega en `serialization::load()`
(`src/settings/serialization.rs:47`) que hace `serde_json::from_str` puro — si el JSON es
inválido falla con un error serde críptico, pero si el JSON es **válido pero semánticamente
roto** (p.ej. `provider = "local"` con `local_llm_url` vacío o mal formado), **no se detecta
hasta runtime**, cuando un request al LLM explota con un 500 opaco.

El modelo de config relevante es `ModelSettings` (`src/settings/types.rs:214-245`):

```rust
pub struct ModelSettings {
    pub provider: String,
    pub api_flavor: String,
    pub local_llm_url: String,
    pub local_llm_model: String,
    pub embedding_url: String,
    pub embedding_model: String,
    ...
}
```

El módulo `src/settings/validation.rs` existe pero **solo tiene** `non_empty(&str)` (6 líneas).
No hay validación cruzada de campos.

`apply_to_env()` (`src/settings/mod.rs:30` / `src/settings/env.rs`) propaga los campos a
`XAVIER_*` antes de que se construya cualquier cliente.

## 📋 Problema

Configuraciones inválidas para modo local (URL vacía, no-http, modelo vacío, dimensión
inconsistente) pasan el arranque y explotan más tarde con errores crípticos tipo
"connection refused" o "dimension mismatch".

## ✅ Criterio de aceptación

- [ ] Ampliar `src/settings/validation.rs` con funciones nuevas (mantener la existente):
  - `pub fn is_http_url(value: &str) -> bool` — true si parsea con `url::Url::parse` y el
    scheme es `http` o `https`. (Verificar que `url` esté en `Cargo.toml` — si no, usar
    `starts_with("http://") || starts_with("https://")` como fallback simple.)
  - `pub fn validate_local_config(settings: &XavierSettings) -> Result<(), Vec<String>>`
    que recolecte todos los errores encontrados (no solo el primero) y devuelva una lista de
    mensajes legibles:
    - Si `settings.models.provider == "local"` o `"ollama"`:
      - `local_llm_url` no vacío y es http(s). Error:
        `"local_llm_url is empty/invalid: got '{}'. Set it to http://localhost:11434/v1"`.
      - `local_llm_model` no vacío. Error: `"local_llm_model is empty (set qwen3-coder)"`.
      - `embedding_url` no vacío y es http(s).
      - `embedding_model` no vacío.
      - Si `settings.memory.embedding_dimensions != 0`, que sea un valor plausible
        (32..=8192). Error si está fuera de rango.
    - Si `provider == "cloud"` o cualquier cloud específico:
      - Al menos uno de `llm_api_key` o cloud env debe estar presente — soft warning, no
        error fatal.
  - Devolver `Err(vec![...])` con todos los problemas encontrados de una sola vez, o `Ok(())`.
- [ ] Llamar `validate_local_config` desde `src/main.rs` **inmediatamente después** de
  `XavierSettings::load()` y **antes** de `apply_to_env()`:
  ```rust
  if let Some(ref settings) = XavierSettings::load()? {
      if let Err(problems) = settings::validation::validate_local_config(settings) {
          eprintln!("❌ Invalid Xavier configuration:");
          for p in &problems {
              eprintln!("   • {p}");
          }
          eprintln!("\nFix config/xavier.config.json (or run `xavier setup --local`) and retry.");
          std::process::exit(2);
      }
      settings.apply_to_env();
  }
  ```
- [ ] El `apply_to_env` solo se llama si la validación pasa (fail-fast con código de salida 2
  y mensaje humano).
- [ ] No introducir dependencias nuevas: si `url` ya está en el workspace, usarlo; si no,
  quedarse con la heurística `starts_with`.
- [ ] Tests unitarios en `src/settings/validation.rs`:
  - Config local válida → `Ok(())`.
  - `provider=local` + `local_llm_url=""` → `Err` con mensaje claro.
  - `provider=local` + `local_llm_url="ftp://x"` → `Err` con mensaje sobre scheme.
  - `provider=cloud` + todo vacío → `Ok` con warnings (o `Err` según se decida, pero
    consistente).
- [ ] `cargo check --workspace` y `cargo test -p xavier --lib settings` pasan.
