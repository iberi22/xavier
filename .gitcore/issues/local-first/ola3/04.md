# [Ola 3 · 04] `xavier doctor`: comando CLI de diagnóstico de salud local

> Parte de la iniciativa **Xavier 100% Local (LLM + embeddings vía Ollama) — Ola 3**.

## 🎯 Contexto

El wizard `xavier setup --local` (`src/cli/handlers/setup.rs:166`, `handle_local_setup`) ya hace
la mitad del trabajo: usa `SystemScanner::scan().await` (`src/cli/handlers/system_scan.rs:72`)
para detectar Ollama, listar modelos (`scan.ollama.models`), y prueba reachability con
`test_ollama_reachability`. Pero es **interactivo** (usa `dialoguer::Confirm`) y **modifica
config**. No existe un comando **no interactivo, read-only** que un usuario final o un script de
CI pueda correr para saber "¿está todo OK para correr 100% local?".

El dispatch de comandos vive en `src/cli/commands/mod.rs:55` (`Cli::run`), y el enum top-level
es `Command` en `src/cli/commands/enums.rs` (con variantes como `Http`, `Setup`, `Quota`,
`Verify`, etc.). El handler de `Setup` se invoca en `mod.rs:199`:
`Command::Setup { local } => crate::cli::handlers::setup::handle_setup(*local).await`.

Patrón de salida legible ✓/✗ ya existe en `src/cli/handlers/verify.rs:75-97` (tabla ASCII con
iconos de estado).

## 📋 Problema

No hay forma rápida, no interactiva, de responder a:
- ¿Está Ollama corriendo y reachable?
- ¿Están los modelos `qwen3-coder` (LLM) y `embeddinggemma` (embeddings) instalados?
- ¿Apunta la config a `provider=local` con una URL válida?
- ¿Es accesible la DB y el vector store?
- ¿Coincide el modelo de embedding activo con el que generó los vectores (issue 02)?

## ✅ Criterio de aceptación

- [ ] Añadir la variante al enum en `src/cli/commands/enums.rs` (cerca de `Setup`, línea ~167):
  ```rust
  /// Diagnose local-first health (Ollama, models, DB, config, vector store)
  #[command(name = "doctor")]
  Doctor {
      /// Output format: table (default), json, markdown
      #[arg(long, default_value = "table")]
      format: String,
  },
  ```
- [ ] Despacharla en `src/cli/commands/mod.rs` (cerca de la línea 199):
  ```rust
  Command::Doctor { format } => {
      crate::cli::handlers::doctor::handle_doctor(format.clone()).await
  }
  ```
- [ ] Crear `src/cli/handlers/doctor.rs` con `pub async fn handle_doctor(format: String)
  -> Result<()>` que ejecute estas checks y arme un `DoctorReport` (struct serializable):
  1. **Ollama reachability** — reusar `SystemScanner::scan().await` (ya detecta Ollama y
     versiones en `src/cli/handlers/system_scan.rs:90`, `detect_ollama`). Marcar ✓ si
     `scan.ollama.running == true`.
  2. **Modelos instalados** — leer `scan.ollama.models` y verificar que contenga
     `qwen3-coder` (LLM) y `embeddinggemma` (embeddings). ✓ por modelo.
  3. **Config válida para local** — cargar `XavierSettings::load()?` y comprobar
     `settings.models.provider == "local"`, que `settings.models.local_llm_url` sea una URL
     http(s) no vacía (validar con `url::Url::parse`), y que
     `settings.models.embedding_model` no esté vacío.
  4. **Reachability de la URL configurada** — hacer `reqwest::get(local_llm_url + "/api/version")`
     con timeout corto (2s) y reportar código HTTP.
  5. **DB access** — abrir `vec-store.sqlite3` (path desde `XAVIER_MEMORY_VEC_PATH` o default)
     y hacer `SELECT count(*) FROM memory_records`. ✓ si responde sin error.
  6. **Vector store operativo** — `SELECT count(*) FROM memory_embeddings`. Reportar el número.
  7. **Embedding model consistente** (opcional, soft) — si existe la tabla
     `embedding_model_meta` (issue 02), comparar `active` con `settings.models.embedding_model`.
     Si difieren, ✗ con hint "Run /memory/reindex".
- [ ] Imprimir el reporte en formato `table` (iconos ✓/✗ + detalles, estilo `verify.rs`),
  `json` (`serde_json::to_string_pretty`) o `markdown` (tabla pipe).
- [ ] Código de salida: `0` si todas las checks críticas (1-6) son ✓, `1` si alguna falla.
- [ ] Añadir `pub mod doctor;` a `src/cli/handlers/mod.rs`.
- [ ] Test unitario: `DoctorReport` se serializa a JSON sin panic.
- [ ] `cargo check --workspace` y `cargo test -p xavier --lib doctor` pasan.
