# [Ola 2 · 11] Timeout y circuit breaker por provider en el `ProxyUseCase`

> Parte de la iniciativa **Xavier 100% Local (LLM + embeddings vía Ollama) — Ola 2**.
> Evita que un provider tóxico (siempre cae) consuma tiempo en cada mensaje.

## 🎯 Contexto

`ProxyUseCase::execute_secured` (`src/app/proxy_use_case.rs:203`) ya tiene:

- Un timeout global por request: `tokio::time::timeout(LLM_TIMEOUT, ...)` en línea 387 (`LLM_TIMEOUT` importado de `src/agents/provider/config.rs`).
- Un reintento **mismo-provider** para 429 (líneas 475–483, `retry_count < max_retries`).
- El fallback **entre providers** lo añade el issue 02 (reintento con provider distinto).

Lo que **falta** es un circuit breaker: si el provider `X` falla N veces consecutivas, debe
quedar marcado como temporalmente "abierto" (rate-limited) durante una ventana (p.ej. 60s) para
que el `ProxyUseCase` no intente seleccionarlo de nuevo en cada mensaje y pierda tiempo.
`RateLimitManager` ya expone `get_status(provider).rate_limited_until` (ver línea 247) y se
consulta en la selección de provider — basta con que el brazo de error **marque** ese campo.

## 📋 Problema

Hoy, si un provider cae, se reintenta en cada mensaje (el `rate_limited_until` solo se setea
para 429 reales del provider, no para fallos 500/timeout que vemos nosotros). Resultado: cada
mensaje paga el coste del timeout de un provider muerto.

## ✅ Criterio de aceptación

- [ ] Añadir una constante `CIRCUIT_BREAKER_FAILURE_THRESHOLD: u32 = 3` (configurable vía env `XAVIER_CB_FAILURES` si conviene) y `CIRCUIT_BREAKER_OPEN_SECS: i64 = 60` en `proxy_use_case.rs`.
- [ ] Mantener un contador de fallos consecutivos por provider. Como `ProxyUseCase` es `Sync + Arc`-compartido, usar un `parking_lot::Mutex<HashMap<String, u32>>` añadido como campo `provider_failures` al struct (similar a `prompt_cache` línea 26). Resetear a 0 en éxito.
- [ ] En cada brazo de error de `execute_secured` (líneas 495, 509, 521 — los que devuelven `ProxyError::ProviderError` por fallo/timeout), incrementar el contador para `provider_name`. Si alcanza el threshold, llamar a `self.rate_manager` para marcar `rate_limited_until = now + CIRCUIT_BREAKER_OPEN_SECS` (verificar qué método de `RateLimitManager` permite setear esto; si no existe, añadirlo como `mark_rate_limited(provider, until)` en `src/agents/rate_limit.rs` — en ese caso este issue sí toca ese archivo). Loguear `warn!("Circuit breaker OPEN for {}", provider_name)`.
- [ ] En el brazo de éxito (línea 394 `Ok(Ok(resp))`), resetear el contador del `provider_name` a 0.
- [ ] El comportamiento del issue 02 (fallback entre providers) y de la selección inicial (issue 01) queda **reforzado**: al saltar el circuit breaker, la próxima selección evita automáticamente el provider tóxico porque `rate_limited_until` ya está seteado.
- [ ] Test unitario: simular 3 fallos consecutivos de un provider mock y verificar que en la 4ª llamada `get_status(provider).rate_limited_until` está en el futuro (provider excluido de la selección).
- [ ] `cargo check -p xavier` y `cargo test -p xavier --lib proxy_use_case` pasan.
