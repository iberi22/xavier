# [Ola 2 · 03] Degradación elegante: responder desde memoria cuando TODOS los providers fallan

> Parte de la iniciativa **Xavier 100% Local (LLM + embeddings vía Ollama) — Ola 2**.
> Última red de seguridad del chat. No debe impedir que el usuario siga trabajando
> aunque no haya ningún LLM disponible (ni cloud ni local).

## 🎯 Contexto

Hoy, cuando `execute_secured` falla por completo, el handler del chat devuelve un error y el
usuario ve en el panel un mensaje tipo **"No pude contactar al modelo de IA"** — la
conversación se atasca aunque Xavier tenga memoria indexada perfectamente utilizable.

El `AgentRuntime` (`src/agents/runtime.rs`) ya resuelve este caso con `System3Actor::simple_response`
(`src/agents/system3/engine.rs:276`), que produce una respuesta heurística a partir de los
documentos recuperados de la memoria. Esa misma idea debe portarse al handler del chat del panel.

El handler real del chat vive en `src/cli/handlers/headless_api.rs:106 headless_chat` (es el
que llama `execute_secured` en la línea 124). El `panel_process_chat_inner`
(`src/cli/handlers/panel.rs:122`) hoy es un **stub** que no llama al proxy — cuando se cablee
al proxy (trabajo paralelo), esta degradación aplica igual.

`CliState` ya expone la memoria: `state.memory: Arc<dyn MemoryQueryPort>` (línea 33) con el
método `search(query)` (`src/ports/inbound/memory_port.rs:10`).

## 📋 Problema

1. Fallo total de providers → mensaje de error crudo → UX rota.
2. Toda la memoria indexada queda inutilizada cuando más falta hace (cuando el LLM no responde).

## ✅ Criterio de aceptación

- [ ] En el brazo `Err` de `headless_chat` (`src/cli/handlers/headless_api.rs:132-134`, hoy solo hace `ProxyErrorWrapper(e).into_response()`), **antes** de devolver el error 5xx:
  1. Se extrae el último mensaje del usuario del `req.messages`.
  2. Se llama `state.memory.search(...)` con ese texto (usar `MemoryQueryPort::search`, top-k 5).
  3. Si hay al menos 1 resultado, se construye una `ChatResponse` **sintética** cuyo `choices[0].message.content` sea un resumen de los documentos recuperados (puede reusarse o reimplmentarse la heurística de `System3Actor::heuristic_answer` / `simple_response` — idealmente extrayéndola a un util compartido, pero **sin** tocar `engine.rs` si eso rompe el aislamiento del issue; basta una función local `fallback_from_memory(query, docs) -> String`).
  4. Se añade al `ChatResponse` un campo de metadato `provider: "memory-fallback"` (extender el struct `ChatResponse` en `headless_api.rs:83` con `#[serde(skip_serializing_if = "Option::is_none")] pub provider: Option<String>` y devolver HTTP 200, **no** 5xx).
  5. Si no hay resultados en memoria, se mantiene el error actual (no se inventa contenido).
- [ ] El `panel_process_chat_inner` (`src/cli/handlers/panel.rs:122`) aplica la misma degradación cuando se cablee al proxy; mientras sea stub, al menos dejar un `// TODO(issue 03): memory-fallback` en el sitio donde iría el `match` sobre el resultado del proxy.
- [ ] El mensaje al usuario es claro: no se hace pasar por una respuesta del LLM. Encabezado tipo `"[Modo memoria — LLM no disponible] "`.
- [ ] Se emite log `warn!` con el fallo original del provider para que no se pierda en telemetría.
- [ ] `cargo check -p xavier` pasa.
- [ ] Test unitario en `headless_api.rs` (o en un módulo `#[cfg(test)]`) que, dado un `MemoryQueryPort` mock que devuelve 2 docs y un `proxy_use_case` mock que falla, verifique que la respuesta es 200 con `provider == "memory-fallback"`.
