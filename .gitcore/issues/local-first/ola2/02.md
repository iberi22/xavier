# [Ola 2 · 02] Cablear `ProviderRouter` al `ProxyUseCase` (fallback ante fallo, 1 reintento)

> Parte de la iniciativa **Xavier 100% Local (LLM + embeddings vía Ollama) — Ola 2**.
> Continuación directa del issue 01 (que solo añade `local` al array de candidatos).
> Este issue **sí** implementa el reintento con proveedor distinto.

## 🎯 Contexto

`ProviderRouter` (`src/agents/provider/router.rs`) ya expone toda la maquinaria:

- `build_default_chain(configured)` (línea 147) — construye la cadena poniendo `Local` al final si Ollama es reachable.
- `set_fallback_chain(chain)` (línea 205).
- `on_provider_failure()` (línea 213) — devuelve el siguiente provider de la cadena o `None`.
- `fallback_chain()` (línea 299), `current_provider()` (línea 264).

Y el `ProviderRouter` **ya está vivo** en el `CliState`:

```rust
// src/cli/state.rs:68
pub provider_router: Arc<tokio::sync::RwLock<xavier::agents::provider::router::ProviderRouter>>,
```

El problema: `ProxyUseCase::execute_secured` (`src/app/proxy_use_case.rs:203`) **no usa** ese router.
Cuando el proveedor elegido falla (brazo `Ok(Err(e))` línea 462, o el timeout línea 512), devuelve
`ProxyError` directamente. No hay reintento con otro provider.

`ProxyUseCase` actualmente no tiene acceso al router — hay que pasárselo.

## 📋 Problema

Si el proveedor seleccionado cae (500/timeout/429 agotado), el chat falla aunque haya otros
providers disponibles en la fallback chain (incluido `local`). El router existe pero está
desconectado del use case.

## ✅ Criterio de aceptación

- [ ] `ProxyUseCase` gana un campo opcional `provider_router: Option<Arc<tokio::sync::RwLock<ProviderRouter>>>` y un builder method `with_provider_router(router)` (mismo patrón que `with_threat_detector` / `with_event_bus` en `proxy_use_case.rs:46/51`).
- [ ] En `server.rs` (cerca de la línea 376 donde se construye el `CliState`), el `proxy_use_case` se enriquece con `.with_provider_router(state.provider_router.clone())`. **Ojo:** el orden de construcción importa — el router se crea en la línea 351, hay que pasarlo al `proxy_use_case` antes de construir el `CliState`. Revisar el flujo.
- [ ] En el brazo `Err` de `execute_secured` (las ramas que hoy hacen `return Err(ProxyError::ProviderError(...))` líneas 495/509/521), **antes** de devolver el error, si `self.provider_router` está presente y no se ha agotado el reintento, se:
  1. Llama `router.write().await.on_provider_failure()` → `Option<ProviderKind>`.
  2. Si devuelve `Some(next)`, se mapea a `String` (con `kind.as_str()`) y se reintenta **una sola vez** con ese provider (re-construyendo el `ModelProviderConfig::for_provider(&next_name)` y re-entrando al loop con `retry_count += 1`).
  3. Si devuelve `None` o ya se reintentó, se devuelve el error original.
- [ ] **Máximo 1 reintento** con proveedor distinto (no recursión infinita). Usar un flag/contador local; no reusar el `retry_count` existente que hoy se reserva para 429-mismo-provider.
- [ ] El reintento solo aplica a fallos de provider (500/timeout/error de red), **no** a `ProxyError::RateLimited` del lease token ni a `SecretError` ni a `InvalidRequest` (security).
- [ ] Se emite un log `warn!` claro: `"Provider {old} failed, falling back to {next}"`.
- [ ] `cargo check -p xavier` pasa.
- [ ] Test unitario: mock del `ProviderRouter` (o router real con `set_fallback_chain([OpenAI, Local])`) que verifique que tras un fallo simulado, el segundo intento usa el siguiente provider. Si mockear el fallo HTTP es inviable sin mockito, al menos un test de la lógica de "seleccionar siguiente provider tras fallo" aislándola en una función auxiliar.
