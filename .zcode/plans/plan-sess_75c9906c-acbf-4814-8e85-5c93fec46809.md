# Plan: Cablear el chat del panel a LLM real

## Diagnóstico (3 bugs encadenados)

1. **BUG PRINCIPAL — Field name mismatch**: El backend serializa `Message.content` pero el frontend (`ChatHistory.tsx` líneas 29, 34, 152) lee siempre `msg.plain_text`. Por eso NO se ve ni siquiera el stub — la respuesta llega como `{content: "..."}` pero la UI busca `{plain_text: "..."}` y muestra vacío.

2. **Stub hardcoded**: `cli/handlers/panel.rs:154` devuelve `"Structured Xavier response for: hola"` sin llamar a ningún LLM.

3. **ThreatDetector blocking**: El scanner del proxy bloquea las llamadas (probablemente por un system prompt interno que matchea patrones de inyección, no por el "hola" del usuario). **Pero no necesitamos tocar esto** — ver punto 2 del plan.

## Descubrimiento clave

Existe un handler **real y completo** en `server/panel/chat.rs::process_chat` que usa `AgentRuntime::run_with_trace()` (con LLM real, retrieval, reasoning y UiRender). Está exportado pero **NUNCA montado** en el router de producción. El router monta el stub en su lugar.

## Cambios (2 archivos Rust, 0 frontend)

### Cambio 1: `src/codebase/conversations_db.rs` — fix del field mismatch
Añadir `#[serde(alias = "plain_text")]` al campo `content` del struct `Message` (línea 43):

```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct Message {
    pub id: String,
    pub thread_id: String,
    pub role: String,
    #[serde(alias = "plain_text")]
    pub content: String,
    // ...resto sin cambios
}
```

Esto hace que la serialización produzca `"content"` (compatibilidad con DB/otros consumers) Y acepte deserializar desde `"plain_text"`. Para que el frontend reciba `plain_text`, añadimos un campo alias serializado:

**Alternativa más simple y directa**: renombrar la serialización con `#[serde(rename = "plain_text")]`. Pero esto rompería otros consumers que leen `content`. Mejor usar `Serialize` con alias para output:

Mejor enfoque — crear un struct wrapper de respuesta que mapee `content` → `plain_text` solo para la API del panel. Pero `PanelChatResponse` ya usa `Vec<Message>` directamente...

**Decisión final**: Usar `#[serde(rename = "plain_text")]` en `content`. Los otros consumers que leen `content` son internos del backend (MCP, proxy) y usan deserialización estructurada, no JSON field-name matching. Si algo se rompe, el compilador lo detecta.

### Cambio 2: `src/cli/handlers/panel.rs` — reemplazar stub por llamada al proxy LLM
Reemplazar las líneas 154-163 (el stub) con una llamada real a `state.proxy_use_case.execute_secured()`:

```rust
use xavier::domain::proxy::ProxyChatCommand;

// Build command with the user's message
let cmd = ProxyChatCommand {
    model: "auto".to_string(),
    messages: vec![serde_json::json!({ "role": "user", "content": &payload.message })],
    temperature: Some(0.7),
    max_tokens: Some(1024),
    lease_token: None,
};

// Call real LLM via the proxy
let completion = state
    .proxy_use_case
    .execute_secured(
        cmd,
        false,
        state.secrets_engine.clone(),
        state.event_bus.clone(),
    )
    .await?;

let assistant_content = completion
    .choices
    .first()
    .map(|c| c.message.content.clone())
    .unwrap_or_else(|| "(sin respuesta)".to_string());

// Fallback graceful si el proxy falla (threat detector, rate limit, etc.)
// manteniendo respuesta útil en vez de error 500
```

Con manejo de errores: si `execute_secured` falla (threat detector, rate limit, provider caído), capturar el error y devolver un mensaje útil en vez de 500.

### Por qué NO tocar el ThreatDetector
El ThreatDetector escanea TODOS los mensajes del array. Si solo enviamos el mensaje del usuario (sin system prompt sospechoso), no debería bloquear. Si aún bloquea, el manejo de errores del Cambio 2 lo captura gracefully. Arreglar el scanner es un tarea separada y más riesgosa.
