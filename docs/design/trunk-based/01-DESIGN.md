# Trunk-based flow for Xavier

Status: proposed; activated only after ADR-035 acceptance and the branch-rule work in Phase 3. This design changes integration policy, not the release process. `main` is the trunk; working branches should last hours, with a 24-hour review trigger rather than an unenforceable four-hour expiry. One code feature (or bounded part) per PR, with its feature ID, remains the unit of change (`AGENTS.md:51-55`, `AGENTS.md:80-84`).

## 1. Two CI lanes

Keep the current CI observable during transition. The present workflow runs on PRs and `main` pushes (`.github/workflows/ci.yml:3-8`), but its full Rust test median is 9.7 minutes and Clippy median 3.2 minutes (`facts/FACTS.md:4-5`). The new always-present `fast-gate` result is the only general required status check after it proves reliable. Its result must be **failure** when path classification is unknown, a job fails, or the workflow is cancelled; never treat a skipped check as success.

| Fast-gate job | Trigger and command shape | Target budget (including runner queue) |
| --- | --- | --- |
| `classify` | Always run; compare PR base/head; record paths, actor, risk class, reverse dependencies and classification in job summary. Reject unknown paths, >4 files or >400 changed lines from agent Ship, mixed high-risk paths, and a label that understates risk. | 20 s |
| `policy-security` | Every PR: staged/diff strategy and forbidden-file checks, path safety, version sync, `scripts/verify-pipeline.sh --check-only`, and full `scripts/check-secrets.sh` on the PR checkout. Require gitleaks or fail rather than use its weaker fallback in CI. | 45 s |
| `rust-scoped` | Only Rust-impacted PRs: `cargo fmt --all -- --check`; `cargo check` on impacted packages and reverse dependents with `ci-safe`; package-scoped Clippy and unit tests selected by the impact map. Run `-D warnings`. No blind test-name grep or zero-test success. | 150 s warm-cache goal |
| `ui-scoped` | `panel-ui/**` and shared UI contract changes: TypeScript check/unit tests/build as relevant; preserve the bundle token-canary before merge for UI changes. Browser smoke remains async on every `main` push. | 150 s goal |
| `fast-gate` | Always-run final job with `if: always()`, depends on all above; fail if any required selected job failed, was cancelled, or did not report; succeed for docs-only changes only after policy/security passes. Stable check name for ruleset. | < 180 s p90 for eligible PRs |

All budgets are targets, not current measurements. Jobs run in parallel. The 180-second goal applies to eligible PRs; publish separate results for Ask, cold cache and conservative fallbacks. If `cargo check` or a test target cannot reliably finish, keep it required and accept a slower gate until code/test isolation or caching is proven. Do not move a failing safeguard async solely to hit the number. The existing `rust-clippy` job checks only package `xavier` (`.github/workflows/ci.yml:69-92`); the new impact map must cover the workspace dependencies too (`Cargo.toml:40-59`, `Cargo.toml:247-250`).

**Rust impact map, first version.** Generate package ownership from workspace manifests, then maintain a small explicit reverse-dependency map. `src/**` selects `xavier`; `crates/xavier-core-logic/**` selects that crate and `xavier`; `code-graph/**` selects changed parser/crate, `code-graph` and `xavier`; `crates/xavier-wasm/**` selects WASM plus its dependents. `tests/**` selects the owning test target and root crate. `Cargo.lock`, root/workspace manifests, `.cargo/**`, `build.rs`, `vendor/**`, CI/impact scripts, or an unknown file select all affected workspace packages and trigger a conservative full pre-merge path if the selected checks exceed the fast budget. Root library tests are serial by necessity (`.github/workflows/ci.yml:144-154`); initially run them before merge for source changes unless a module-to-test mapping has shown, against historical PR failures and shadow runs, that selected tests catch the same failures. A zero selected-test result fails. Do not infer safety from an unrelated green package. `panel-ui/src-tauri` is excluded from the root workspace (`Cargo.toml:40-47`); classify it separately and require an explicit build/test recipe before it can use Ship or Show.

**Async post-merge lane.** On every new `main` SHA, run full root library tests, workspace package tests where CI-safe, the observability integration target, browser smoke for every change, full Clippy/MSRV, full ledger `scripts/verify-pipeline.sh`, coverage and available audits; schedule any service-dependent E2E against a controlled environment. Current root tests and the single observability target are documented in `.github/workflows/ci.yml:116-182`; current browser smoke deliberately runs on all changes (`.github/workflows/ci.yml:198-254`). Keep coverage report-only until the tarpaulin parser issue is fixed (`.github/workflows/rust-coverage.yml:20-53`). A test requiring unavailable services is reported as **not run**, never green. Scope expensive perf to scheduled/release runs, with a baseline and regression threshold before using it as a failure signal. Secrets and token-canary checks stay pre-merge, not only async (`.github/workflows/ci.yml:184-196`, `.github/workflows/ci.yml:230-245`).

**Failure response.** A failed `main` run opens or updates one `tbd-incident` issue keyed by SHA, linking failed jobs, change PR, owner and run logs, then notifies the owner in GitHub. The current Jules notifier exits for `main` failures (`.github/workflows/jules-ci-feedback.yml:29-40`); extend or replace that path. For a single confidently attributable, unreleased, reversible commit, automation may open an **auto-revert PR** with the inverse diff and fast gate, then request owner review; never force push, never silently auto-merge a rollback, and never revert a schema/data migration mechanically. For uncertain attribution, a migration, a security incident or a released/tagged commit, file the issue and have the owner coordinate a fix or rollback. Close the incident only after the fix/revert SHA is green. A reverted commit does not undo a local binary deployment or published tag (`facts/FACTS.md:9`; `.github/workflows/release.yml:3-8`). For Pages failure, treat the deploy run as an incident and redeploy or revert docs through the normal PR path (`.github/workflows/deploy-docs.yml:3-12`, `.github/workflows/deploy-docs.yml:53-63`).

## 2. Ship / Show / Ask as review timing

GitHub labels: exactly one of `flow:ship`, `flow:show`, `flow:ask`; automation computes the **minimum** class from paths and diff. An agent may request a stricter class but cannot downgrade it. Labels do not bypass the fast gate. All agent changes use PRs. Identify the human owner from an explicit GitHub login allowlist; classify every other account, bot and token as an agent. Never trust a self-declared PR checkbox or author label. The owner can edit a classification only by adding a reviewable rationale to the PR; protected path rules still win.

| Class | File/path rule and examples | Human | Autonomous agent |
| --- | --- | --- | --- |
| **Ship** | Docs prose under `docs/**` excluding `docs/design/**`, `docs/adr/**`, `docs/SRS/**`, `docs/features/**`, `docs/site/src/content/docs/{security,install}/**`; comments, spelling, tiny UI text/style under `panel-ui/**` with no auth/API/build/config changes. Max 4 files/400 changed lines; no generated artifacts. Docs Ship still triggers Pages deployment (`.github/workflows/deploy-docs.yml:3-12`). | Short PR, auto-merge after gate; owner emergency bypass only by documented exception. | Allowed via PR and auto-merge after gate; no direct push. |
| **Show** | Bounded internal refactor in `src/**`, `crates/**`, `code-graph/**`, or non-sensitive UI code; behavior preserved with tests; no public API, migration, auth, crypto, permissions, config default, feature activation or CI/ruleset change. Explicit impacted tests and feature ID. | PR, gate then auto-merge; notify owner for review within one business day. | Allowed via PR only after gate and independent diff review by orchestrator/another agent; owner receives post-merge review request. |
| **Ask** | `docs/design/**`, `docs/adr/**`, `docs/SRS/**`, `docs/features/**`, `.gitcore/**`, `.github/**`, `.husky/**`, `scripts/check-secrets.sh`, `scripts/verify-pipeline.sh`, `Cargo.toml`/`Cargo.lock`, `.env.example`, schema/migrations, public HTTP/CLI/MCP contracts, auth/crypto/security, release/deploy and any ambiguous or mixed-risk change. | Owner approval before merge. | May author a PR; owner approval required before merge. No agent may accept an ADR or change branch rules. |

Default unknown paths to Ask. A diff touching a higher-risk path takes the higher class. Treat new code behind a flag as Show only when it cannot execute under current defaults, has no public contract/schema/security change, and the flag itself has a documented owner and removal date; otherwise Ask. The proposed blanket rule “flagged code = Ship” is unsafe here. A code PR references one feature ID per `AGENTS.md:80-84`; docs-only maintenance uses an issue link instead. Ask review response target is <1 business hour during the owner's available hours, measured from `ready_for_review` to first substantive review; if missed, wait rather than auto-merge. Four hours is a branch-age prompt, not a reason to skip review.

## 3. Branch rules and merge mechanics

Owner configures a single active `main` ruleset: no deletion/force push; require PR; require the stable `fast-gate` status on the current SHA; require conversation resolution; allow auto-merge and squash; require owner approval for `flow:ask` by a ruleset or a required classification check that verifies approval from the owner after the latest change. Ensure a contributor cannot self-approve. For Ship/Show, a policy check confirms the class and permits auto-merge without prior owner review. If GitHub rules cannot express conditional approval securely, use a separate required `policy` check that fails until Ask approval is observed. Re-evaluate it on PR open/update, label changes and review submissions; it must be attached to the current head SHA and use a read-only token for untrusted PR code. Turn on merge queue only if concurrent PRs produce stale results; otherwise require branches up to date before merge. Trial the ruleset on a non-default branch, then enable after shadow gate reliability and recovery drills.

Only the human owner holds any direct-`main` bypass, for a documented emergency with a linked incident and immediate follow-up PR/check. Agents and bot tokens have no bypass or direct-push permission. This is a deliberate departure from direct Ship pushes: under the current rules, such pushes have no required check (`facts/FACTS.md:2`). Do not enable direct push as Phase 3 simply because the calendar reaches week three.

## 4. Hooks and code migration conventions

Keep `.husky/pre-commit` and `.husky/pre-push` (`AGENTS.md:90`; `.husky/pre-push:1-5`). Pre-commit should enumerate `git diff --cached --name-only -z --diff-filter=ACMR`, inspect staged **index blobs** (including new files), reject runtime DBs, paths and staged strategy/secret leaks, and run `rustfmt` only on staged `.rs` files without modifying unstaged content. Move full `cargo fmt --all`, Clippy and UI build to CI/on-demand pre-push, since the current hook does whole-project work (`.husky/pre-commit:15-55`). Do not let absence of Node silently disable the pre-push guard; fail with an actionable message or provide a shell equivalent (`.husky/pre-push:3-5`). The CI scan must fail if gitleaks is unavailable; the local fallback remains a convenience, not security evidence (`scripts/check-secrets.sh:15-33`). Never auto-stage changes in a hook.

For a long migration, first add a trait/interface at the narrow call boundary, ship an adapter that preserves old behavior, add the new implementation behind a Cargo feature or documented environment toggle, redirect one caller at a time, then remove the old path and toggle after a green post-merge window. Cargo features already separate optional capabilities and `ci-safe` (`Cargo.toml:61-86`); configuration is environment based and new keys must be added to `.env.example` (`AGENTS.md:63-69`). Keep a new runtime flag off by default, name its owner and removal condition in the feature spec, test off/on paths, and use no flag service. A feature flag is not a substitute for review of API/schema/security changes. Release tags and local binary installation remain separate from merge (`.github/workflows/release.yml:3-8`; `facts/FACTS.md:9`).

## 5. Four-phase rollout with exit criteria

| Phase | Work | Exit criterion |
| --- | --- | --- |
| **1. Baseline and hygiene** | Accept ADR and update `AGENTS.md` PR verification wording; record CI/DORA baseline, inventory failed tests, fix actual flakes only if observed, introduce staged Husky changes and a shadow fast gate; restore explicit full ledger execution after merge while PR gets structural verification. | Two weeks of shadow runs with no unclassified PR, no missing secret/ledger results, all failures linked to checks, and a demonstrated `main` incident/revert drill. Existing checks remain visible. |
| **2. Classification** | Add labels, changed-path policy and PR template; trial Ship/Show/Ask on PRs without changing protections. Compare impact-selected checks to full checks. | 100% of sampled PRs have the correct or stricter label, one feature ID/issue link, no missed full-suite failure in the shadow sample; p50/p90 gate times published by path class. |
| **3. Protected integration** | Human owner enables ruleset, required always-run fast gate, auto-merge for eligible Ship/Show; Ask approval remains mandatory. Agents continue to use PRs. | Verify a rejected direct agent push, rejected stale/unclassified PR, blocked Ask without owner approval, successful Ship/Show auto-merge, and automatic incident creation on a simulated `main` failure. If the selected gate misses a full-suite failure, revert to the prior required-check set. |
| **4. Operate and adjust** | Review weekly GitHub metrics; improve cache/test seams, triage post-merge failures, tune only evidenced path mappings. | Four weeks of measured lead time, MTTR, change-failure rate and fast-gate p50/p90; documented response for every red `main` run; retain or roll back the policy based on those results. |

The Skill Controller proposal on `design/skill-controller` can teach agents the labels, scope limits and evidence format. It is advisory: GitHub path classification, status checks and branch rules remain the enforcement boundary. Keep its rollout independent so failure or delay there does not block this policy.
