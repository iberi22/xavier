# DONE protocol

Status: proposed implementation contract, 2026-09-27. This defines what `scripts/done-check.sh` must enforce. It does not declare current tasks, ADR-035 or the pipeline DONE. The independent agent panel decides ADR-035 acceptance; Phase 3 activation and final product acceptance require owner authorization through the Product Acceptance Package.

## Terms and invariant

`DONE` is a computed verdict for an immutable Git SHA, never a checkbox or agent assertion. A new commit invalidates the verdict. `NOT_RUN`, `SKIPPED`, `TIMED_OUT`, `CANCELLED`, missing evidence, stale CI and reviewer `PARTIAL` all fail required gates. The verifier stores a report with individual pass/fail reasons; it never edits the feature ledger or marks Atlas complete on its own. `scripts/verify-pipeline.sh` alone governs ledger promotion after executed tests.

Use one generated JSON evidence bundle per candidate, stored as a GitHub Actions artifact and linked from Atlas evidence strings and the PR. Do not commit the bundle, logs, databases or secrets. The canonical bundle fields are `schema_version`, `level`, `repository`, `session_id`, `feature_id` or `issue_url`, `task_ids`, `base_sha`, `head_sha`, `allowed_paths`, `changed_paths`, `commands`, `ci_runs`, `reviews`, `artifacts`, `risk`, `rollback`, and `created_at`. Each `commands[]` item contains `argv` (array, no shell-evaluated claim), `cwd` relative to repo, `runner`, `sha`, `started_at`, `ended_at`, `exit_code`, `test_count` where applicable, and log artifact URL plus digest. Each `ci_runs[]` item contains workflow/job, run URL, head SHA, conclusion and completion time. Each `reviews[]` item contains backend/model, subject SHA, exact verdict, report URL/digest and unresolved blocking count. Atlas free-form evidence contains these artifact URLs and SHAs, not private paths or copied secrets. The verifier rejects unknown schema versions and duplicate IDs.

## Three DONE levels

| Level | Required evidence bundle | Verifier and pass condition |
| --- | --- | --- |
| **Task DONE** | Atlas task ID/DoD and evidence count; scope allowlist and actual diff; source/test SHA; independent command logs; one cross-model code/design review; risk or `none`; rollback note | `done-check --level task` checks Atlas `--json verify`, all DoD checked, ≥1 evidence, task state `IN_PROGRESS`, size ≤4 changed files/400 changed lines, allowed-path subset, no out-of-worktree writes, path/secret scans, every declared task command executed successfully on head SHA, tests selected nonzero, exact reviewer approval and zero blocking defects. Only then coordinator runs `atlas task complete <id>` (or event `complete --ok` followed by `tick --once`) and confirms state `COMPLETED`. |
| **Feature/epic DONE** | Feature spec/SRS mapping or maintenance issue; DAG with all required task bundles; one code PR/feature ID; CI checks and PR/merge SHA; full `verify-pipeline.sh` report with executed declared tests; review/ADR report; migration/rollback result | `done-check --level feature` checks every dependency/task `COMPLETED` with matching immutable SHAs, no open blocker, spec and ledger reference agree, PR scope/class/policy correct, required current-head CI green, actual merge SHA on `main`, and full ledger execution green for that SHA. `cargo` must exist before full verifier; no skipped full tests. Feature status is read from the ledger after its authorized pipeline promotion; script cannot set it. An unpromoted or contradictory ledger status fails. |
| **Product increment DONE** | Set of feature bundles; main SHA and full CI run URL; smoke/acceptance scenario results; deploy/release candidate and checksum if applicable; known risks; rollback instructions; one-page Product Acceptance Package | `done-check --level increment` checks all constituent features DONE, main CI for the same SHA green (including browser smoke and full ledger), any triggered Pages/release/deploy result linked and green, no unresolved incident for the SHA, acceptance scenarios executed, package links resolve and artifact checksum matches. For outward actions awaiting owner authorization, mark package `READY_FOR_ACCEPTANCE` and list them as pending; do not claim published/deployed DONE. After owner accepts product and authorizes any pending action, record the resulting URL/SHA and rerun increment check. |

Evidence about service-dependent tests uses `NOT_RUN` with reason when no controlled environment exists. If that test is required for the affected feature, the feature stays blocked; if explicitly optional/report-only, the package lists the gap and its owner. Coverage is report-only until the known parser problem is repaired. A docs-only PR still needs policy, path and secret checks, although Rust jobs may be legitimately not selected by the recorded impact map. Docs that trigger public Pages deployment require pre-merge panel review; if the owner has not pre-authorized that publication class, merge waits. Reversible public docs publication is listed in the next Product Acceptance Package. The current root CI has no full ledger job; adding one is a prerequisite for claiming feature/product DONE.

## Exact `done-check.sh` checks

Interface: `scripts/done-check.sh --level task|feature|increment --bundle <json> --repo <checkout> [--task <id>]`. The script should emit machine-readable `verdict`, `sha` and `checks[]` (`id`, `status`, `evidence_url`, `reason`) plus a short text summary, and exit 0 only on `DONE`; 1 for a failed check, 2 for malformed input/unavailable verifier. A report-only or shadow mode may emit the same diagnostics but cannot be used to mark DONE. No `eval` of bundle content.

1. **Bind identity:** validate schema and required fields; `git rev-parse HEAD == head_sha`; all SHAs full length; verify PR head or merge ancestry as appropriate; compare GitHub API's check-suite `head_sha` with bundle SHA. Reject future/unfinished timestamps, unresolved URLs and missing artifacts. Check SHA after every potentially mutating command.
2. **Recompute scope:** use `git diff --name-status -z <base_sha>...<head_sha>` including renames/deletions, plus untracked/staged state in the executor worktree. Normalize each path, reject `..`, absolute paths, symlink escapes, submodule surprises, runtime DB/log/env files and changed paths outside `allowed_paths`. Count actual files and added+deleted lines from `git diff --numstat -z`; task limit is 4/400. Compare recomputed paths with bundle list. Compare before/after snapshots of all task-known worktrees; any unassigned write fails.
3. **Scan committed content:** inspect added lines and complete new text blobs at candidate SHA for personal absolute paths and forbidden roots; run the repo's strategy-leak and `scripts/check-secrets.sh`/gitleaks checks, requiring scanner availability in CI. A generated secret report may be linked, but must not expose matches in public artifacts. A local Husky result does not replace CI.
4. **Execute claims:** expand the task's declared commands from the accepted Atlas/DAG manifest, not from the agent's success prose. For each required command, re-run in a clean checkout at `head_sha` or match a trusted CI job that executed the exact argv on that SHA. Capture argv, start/end, exit code, log digest and test count. Require exit 0, no timeout and ≥1 selected test where a test command was required. No exact match means `NOT_RUN`. Run `scripts/verify-pipeline.sh --check-only` for PR structure; for feature/increment run full `scripts/verify-pipeline.sh` with `cargo` present and require log evidence that declared tests actually ran. Compare declared test filters with observed executions; any zero-match fails.
5. **Check CI independently:** query GitHub Actions for required jobs and `fast-gate` at PR head, and full main jobs at merge SHA. Require `success`, completed and fresh head SHA; fail on absent, skipped, neutral, cancelled or timed-out required jobs. Check policy-computed Ship/Show/Ask class against exactly one label; Ask requires pre-merge approval by two independent agent-panel models, neither the author. Independently require guardian evidence and pre-merge panel review for every rollback revert PR, regardless of class, and never auto-merge one. Outward-publishing changes require pre-merge panel review; Pages-triggering docs cannot use agent Ship auto-merge and need recorded owner pre-authorization of the publication class before merge. Validate one code PR per feature, resolved conversations and merge through PR, never direct agent push.
6. **Check Atlas and review:** parse `atlas --json verify <id>` and `atlas --json dod <id> list` (or equivalent Atlas API) for nonempty/all-checked DoD, evidence count and rule `passed=true`. Require `ATLAS_REVIEW_CMD` configured; `stub:deferred`, `cmd:rejected` and `cmd:deferred` fail even if Atlas says passed. Read the separate review artifact, verify its digest and subject SHA: only exact `APPROVE`/`ACCEPT` with zero blocking defects passes. The reviewer backend must differ from the executor. For ADRs also require the specified simulation command, seed, report digest and two independent panel approvals; do not treat an unevaluated `PENDIENTE` ADR as accepted.
7. **Check closure:** for feature verify complete DAG and ledger status only after the full pipeline; for increment verify all features and main smoke, no open `tbd-incident` on SHA, checksums, trial steps and rollback in the Product Acceptance Package. Ensure every link points to the same SHA or explicitly names a later deployment artifact. Any changed head triggers a fresh run from step 1.

| Required item | Authority checked by the script |
| --- | --- |
| DoD, task state, evidence pointers | Atlas `--json verify`, `dod list` and task state; DONE checker also validates pointed-to artifacts. |
| Scope, leak and secret safety | Git diff/index/worktree snapshots; `scripts/delivery-scope-check.py`; `scripts/check-secrets.sh` and CI `secret-scan` with gitleaks available. |
| Declared tests and feature ledger | Clean-run command logs and nonzero test counts; CI `rust-test`, `rust-integration`, relevant frontend job; full `scripts/verify-pipeline.sh` job on main (to be added). |
| Build/policy checks | Current-SHA CI `rust-fmt`, `rust-clippy`, `rust-msrv`, `frontend-build-audit`, `version-gate` and proposed always-run `fast-gate`/`done` checks, selected by recorded impact map. |
| Independent review | `co-agent-review.sh` report and strict `ATLAS_REVIEW_CMD` adapter; for ADRs, two distinct reviewer models plus required simulation report. |
| Integration and incidents | GitHub PR/reviews/checks API, main run URL, computed flow label, `tbd-incident` query and merge SHA. |

The verifier must compare trusted CI and Git/Atlas records against the bundle. A bundle can point to evidence, but cannot declare itself trusted. `atlas verify` currently checks only checklist presence and evidence count; its reviewer verdict is advisory. `co-agent-review.sh` currently returns success on `PARTIAL`, so the adapter and DONE checker must parse exact verdict text. These are implementation gaps, not accepted passes.

## Product Acceptance Package

Generate one page from the verified bundle and attach/link it to the PR or release candidate. Its headline shows `READY_FOR_ACCEPTANCE` or `ACCEPTED`, product name, main SHA and date. The body has exactly these reader-facing fields:

| Field | Content |
| --- | --- |
| What changed | Outcome in plain language, feature IDs and short demo/result; link to PR/diff. |
| How to try it | Exact setup, safe command or UI path, expected observable result and environment assumptions. |
| Verification | Task/feature counts, required CI job outcomes, full ledger result, smoke result, independent review verdicts and links to runs/reports at the same SHA. |
| Risks | Known limitations, `NOT_RUN` optional tests, incident status and any migration/data impact. |
| Rollback | Revert PR or version restore procedure; distinguish source rollback from installed binary, data and published tag. |
| Decision | One explicit product acceptance choice and separately listed outward/irreversible actions awaiting authorization. |

The generator rejects a package with missing fields or broken evidence links; it never converts a red check to a green summary. If product review finds a defect, open an Atlas task/issue, regenerate evidence at a new SHA and resubmit. Preserve previous package versions as CI artifacts/PR comments for audit.

## States and labels

Atlas task states are its actual `PENDING → READY → IN_PROGRESS → COMPLETED` path, with `BLOCKED` and `FAILED` for dependency or exhausted attempts. `complete --ok` queues an event and needs `tick --once`; `atlas task complete` is the direct completion path. Do not present queued completion as DONE. Atlas evidence strings carry bundle URL/SHA and report URL; task state changes only after the independent checker passes.

GitHub issues use `pipeline:intake`, `pipeline:research`, `pipeline:design`, `pipeline:planned`, `pipeline:implementation`, `pipeline:verification`, `pipeline:integration`, `pipeline:acceptance` as proposed mutually exclusive stage labels, plus `pipeline:blocked` or existing `tbd-incident` when relevant. PRs have exactly one existing `flow:ship|show|ask` label and a computed check status `done/task` or `done/feature`; these are proposed check names, not current jobs. Keep review policy in a required check rather than trusting labels. A merged PR may be `MERGED`, while its feature is still `VERIFYING_MAIN`; mark `FEATURE_DONE` only after the green full main run. Increment states in the acceptance package are `BUILDING`, `READY_FOR_ACCEPTANCE`, `ACCEPTED`, or `BLOCKED`. Labels and package states mirror the verifier result; they never substitute for it.
