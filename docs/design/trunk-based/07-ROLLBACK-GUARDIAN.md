# Independent rollback guardian

Status: proposed design, 2026-09-27. The owner authorizes initial production automation and its credentials through the Product Acceptance Package. After activation, the independent guardian may perform only the reversible rollbacks defined here, then informs the owner through the operator app (Atlas) and a GitHub incident issue. The shipping agent cannot approve its own recovery.

## Production targets and known-good record

| Target | What is production here | Last known-good record and recovery boundary |
| --- | --- | --- |
| Local Xavier binary | The installed `$HOME/.local/bin/xavier` used by the systemd user service, separate from `main` and release publication (`facts/FACTS.md:9`). | Retained, checksum-verified previous binary plus service configuration and successful local health/smoke result. A source revert or release tag does not replace this binary. |
| GitHub release tags | Public release assets and GHCR version and `latest` image tags emitted from `v*` tags; manual dispatch also selects the GitHub publish job, whose tag behavior needs verification (`.github/workflows/release.yml:3-8`, `.github/workflows/release.yml:132-155`, `.github/workflows/release.yml:157-191`). | Recorded prior good version tag, artifact/image digests and validation record. Treat published version tags as immutable; `latest` is mutable but must not be silently retargeted. Prepare a corrective new release from the good revision for owner authorization. Consumers can be directed to the prior version/digest. |
| Cloudflare Pages and Workers apps | A named production deployment/version with a declared route or domain. This repo's inspected workflows do not deploy these apps; each app must opt in with an inventory, health contract, deployment ID and recovery permission. | Prior production Pages deployment ID or Worker version/deployment ID, verified healthy and retained. Verify API, availability and permissions for each target before enabling automation. |
| Xavier docs Pages | The public GitHub Pages site deployed from docs and UI changes on `main` (`.github/workflows/deploy-docs.yml:3-13`, `.github/workflows/deploy-docs.yml:53-63`). | Prior good source SHA, built artifact digest and deployment URL. The current manual dispatch checks out the default branch, so recovery needs a trusted pinned-SHA build/deploy path before automation is enabled (`.github/workflows/deploy-docs.yml:13`, `.github/workflows/deploy-docs.yml:29-51`). |

Keep a per-target append-only mapping of source SHA, deployment/version ID, artifact digest, health evidence, promotion time and previous known-good ID. Promote to known-good only after post-deploy smoke and a stable observation window. A green `main` check alone is insufficient for a running service. Never infer a good target from a tag name or latest deployment.

## Detection and independence

- Trigger immediate post-merge checks on the new `main` SHA and post-deploy checks on the actual production ID. Run smoke against the deployed URL/service, not the build artifact. Sample health endpoint, synthetic user path and error rate where telemetry exists; for Xavier include service state and `/health` (`README.md:139`). Set per-target baselines and thresholds before activation; an unavailable metric is `unknown`, not healthy.
- Run scheduled synthetic probes from outside the shipping workflow. A separate Cloudflare scheduled Worker or independent GitHub Actions workflow can check cloud targets; choose a control plane outside the shipping agent and outside the PC, with separate least-privilege credentials and a protected guardian revision. The shipping workflow cannot disable the live guardian or its schedule. A separate systemd user watchdog/timer monitors the local binary and retains the prior checksum-verified binary. The cloud guardian must continue when the operator PC is off.
- Correlate each result to deployment ID and time. Candidate trigger: failed post-deploy smoke twice, or three failed probes within five minutes plus an error-rate/health signal on the same deployment. Exclude probe outages and unrelated upstream incidents through a second vantage point or telemetry check. Deduplicate by target and deployment ID; pause new promotion during an incident.

## Decision and recovery

The guardian verifies the failing deployment is current, the candidate is the immediately preceding **verified** known-good target, the failure began after promotion, and the target can be restored without a data/schema reversal. It records the evidence and decision before acting. An authorized reversible rollback proceeds automatically, with a lock, one attempt per deployment, a cooldown and post-rollback smoke. If attribution is uncertain, the previous target is missing/unhealthy, the rollback fails, or recovery would change data/schema, credentials or security posture, stop automation and escalate in the incident issue and operator app. Security incidents require containment analysis, not mechanical rollback. Never loop between versions.

| Target | Guardian action when policy passes |
| --- | --- |
| Cloudflare Pages | Restore the prior verified production deployment using the provider's rollback mechanism; verify API and permissions. If unavailable, redeploy the retained immutable good artifact through a separately approved recovery path. Probe the resulting production deployment ID. |
| Cloudflare Worker | Restore the prior verified deployed Worker version with the provider's version rollback/deployment mechanism; verify API and traffic semantics. Probe the resulting route and deployment ID. |
| Xavier docs GitHub Pages | Deploy the retained good artifact or rebuild from its pinned good SHA in a trusted recovery workflow, then run public URL smoke. Verify the GitHub Pages deployment mechanism and artifact retention before activation; do not assume rerunning the current default-branch workflow restores old content. |
| Local Xavier | The separate watchdog atomically points the service at the retained previous binary, restarts the user unit, checks `/health` and smoke, and preserves the failed binary for analysis. It never rewinds the database. If restart/smoke fails, stop retries and escalate. |
| Source code on `main` | Open a git revert PR for a confidently attributable reversible change; attach the guardian's failure, attribution and known-good evidence, run the normal deterministic gates, and require pre-merge review by two independent agent-panel models, neither the author, regardless of Ship/Show/Ask classification. Never auto-merge a rollback revert PR; merge through branch rules after panel approval. No force push. A code revert is distinct from restoring a deployed binary or site. |
| Published release/tag | Do not move the public version tag, overwrite assets or silently retarget GHCR `latest`. Mark the incident, recommend the last good version/digest, and prepare a corrective release with a new tag for owner authorization in final acceptance. |

The rollback guardian sends a review notification with target, detected fault, evidence, decision, action and result to the operator app (Atlas), and opens or updates one GitHub incident issue keyed by target/deployment. Notification failure is itself recorded and retried without hiding the rollback outcome. Link the incident to CI/deploy runs, source SHA, prior and restored IDs, checksums, probe samples, guardian identity, timestamps and panel/owner decisions. Keep secrets and personal paths out of reports. Close only after production smoke and a stable observation window; preserve the failed deployment for investigation where possible.

## Drills and measures

Before enabling any target, rehearse a failed smoke, sustained error signal, false alarm, missing known-good artifact, rollback failure and guardian outage in a nonproduction target. Verify that only the intended version changes, the owner receives both notifications, and a schema/security case escalates without rollback. Repeat after recovery-mechanism changes and periodically thereafter. Report per target: time to detect, time from detection to guardian decision, rollback time, **production MTTR** from first confirmed bad production signal to restored healthy service, false-positive rollbacks, failed rollbacks and unresolved incidents. Keep this production MTTR separate from GitHub integration MTTR (`00-ANALYSIS.md:47-54`).
